# shadcn/ui components

Generated by the shadcn CLI, then edited in place. They are ours once they land —
that is the point of shadcn: it is a generator, not a dependency.

## Adding one

```
cd frontend
npx shadcn@latest add <component>
```

Then do the two things the CLI does not:

1. **Rewrite `@/…` imports to relative ones.** The generated files import through the
   `@/` alias. `tsconfig.json` and `vite.config.ts` both honour it, but
   `eslint-import-resolver-typescript` v4 does not read `paths` out of this project's
   config, so `import/no-unresolved` fails on every generated file. Rather than
   disable a rule that is otherwise doing its job, the four lines get rewritten:

   ```
   import { cn } from '@/lib/utils'   →   import { cn } from '../../lib/utils'
   ```

2. **Check it against `src/styles/index.css`.** Generated components reference shadcn's
   token names — `bg-primary`, `text-destructive`, `border-input`. Those are defined in
   that file, derived from the project's own role tokens, so a component that reaches for
   a name not defined there will render unstyled rather than wrong. Add the token; do not
   hard-code a colour in the component.

## Two house rules these components must keep

- **Logical properties only.** No `ml-`/`mr-`/`pl-`/`pr-`, no `text-left`/`text-right`.
  The platform mirrors for Arabic, and there is a test in `login-page.test.tsx` that
  fails if a physical direction appears in any rendered class.
- **Never communicate status by colour alone.** Always text, or text plus icon.
